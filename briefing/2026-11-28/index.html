Patched Drupal last week? You're not covered yet. Attackers are using a second installer flaw, so update again and check your site

Drupal fixed a second critical flaw in its installer on Nov. 25 and says it is being exploited, including on production sites. Last week's update did not protect against it. Here's what to update, what to block, and what to check if your site was exposed.

On Tuesday we wrote about attackers using Drupal's installer page, `/core/install.php`, to take over websites. That flaw was fixed in Drupal 10.6.22, 11.3.22 and 11.4.13. On Nov. 25 the Drupal Security Team released a second fix, SA-CORE-2026-019, rated Highly critical and tracked as CVE-2026-136716.

What changed. Drupal says "certain sites in unusual or incomplete install states remain vulnerable to site takeover following that advisory, including production sites. It is not apparent in the user interface if a site is in the affected vulnerable state." And: "This is being exploited in the wild." BleepingComputer reported on the new attacks on Nov. 27.

Drupal's compromise-check guide puts it plainly: "Updating to 10.6.22, 11.3.22 or 11.4.13 last week did not protect against this issue." Your site was protected only if requests to `install.php` were blocked or the file was removed, or your host ran Drupal Steward's mitigations. Even then, Drupal says you still need to update.

The fixed versions. Drupal 10.6.23, 11.3.23 and 11.4.14. After updating, run `update.php`. Drupal says "an update hook must run to fix existing production sites in this state." Drupal 11.2.x and older, 10.5.x and older, and Drupal 8 and 9 are end-of-life and get no fix.

Why it matters if you're a small business. If someone on your team or your web agency patched last week and checked the box, the site may still be open. And because the vulnerable state doesn't show up in the admin screens, a site that has run normally for years can still be affected.

Action items for this weekend.
1. Block the installer first. Drupal says this "takes minutes and stops the attack." If you used the Apache or Nginx rule from our Nov. 25 briefing, it's still the right one, and Drupal says sites that already blocked the installer are not vulnerable to this flaw.
2. Update to 10.6.23, 11.3.23 or 11.4.14, then run database updates. Drupal says the code update closes the hole and the database update repairs the recorded install state. Do both.
3. Check the user 1 account. Drupal advises making sure the user 1 email address is one you control and considering a password reset. Whoever manages the site can run:

drush user:information --uid=1

4. Look for admin accounts you don't recognize, and check the recorded install date. Drupal's guide suggests:

date -d "@$(drush state:get install_time)"

That date is set when the installer finishes, so it should match when your site was actually built.

5. Save your web server logs now. Drupal notes some hosts keep logs for only a few days. Its guide includes a command to summarize installer requests since Nov. 18. Constant automated requests for `install.php` are normal. What to look into, per Drupal: POST requests that return 302 or 303, much larger responses, or requests to PHP files in the `files` directory.
6. If anything looks wrong, treat the site as compromised. Drupal warns that updating "does not remove accounts, files or settings that an attacker added." Our own advice: restore from a backup made before the first suspicious request, then update and block the installer before bringing it back online.
