Attackers are using Drupal's installer to take over websites. If your site runs Drupal, here's what to do today

A critical flaw in Drupal core lets an anonymous visitor abuse the leftover installer page to take over a site. Drupal says it has been exploited on live sites since Nov. 19, and CISA added it to its exploited list on Nov. 24. The fix is out, and there's a five-minute block you can add right now.

Every Drupal site ships with an installer page, `/core/install.php`, and it stays on the server long after the site is built. On Nov. 18 the Drupal Security Team rated a flaw in it Highly critical: "Under specific conditions, an attacker can use the installer to attempt to reinstall Drupal. This can lead to a site takeover or remote code execution." It is tracked as CVE-2026-132165.

It's being exploited now. Drupal updated its advisory to say the flaw was "exploited on live sites as early as 2026-11-19 19:00 UTC," BleepingComputer reports. CISA added it to its Known Exploited Vulnerabilities catalog on Nov. 24 and gave federal agencies until Friday, Nov. 27 to fix it.

Which versions are affected. Everything before 10.6.22, 11.0 through 11.3.21, and 11.4.0 through 11.4.12. The fixed releases are Drupal 10.6.22, 11.3.22 and 11.4.13. Drupal 11.2.x and older, 10.5.x and older, and all of Drupal 8 and 9 are end-of-life and get no fix at all, per the Drupal advisory.

Why it matters if you're a small business. You may not know what your website runs on, because a web designer or agency built it years ago. If it's Drupal and nobody has updated it lately, the installer page is probably still reachable: the University of Toronto's security team notes that Drupal's default .htaccess rules do not block it. A taken-over site can be used to serve malware or phishing pages under your name.

Check whether your installer is exposed. Drupal's guide to securing the installer gives these checks. Replace `example.com` with your site's address:

curl -I https://example.com/core/install.php
curl -IL https://example.com/install.php
curl -I https://example.com/core/install.php/foo

All three should end with a `403` or `404`. If you see `200`, the installer is open.

Block it today, even before you patch. On Apache, add this to your virtual host configuration (not .htaccess, which causes a 500 error), run `apachectl configtest`, then reload:

<Location "/core/install.php">
  Require all denied
</Location>

On Nginx, add this inside the HTTPS `server` block, run `nginx -t`, then reload:

location ^~ /core/install.php {
  return 404;
}

Drupal warns not to use an exact match (`location = /core/install.php`), because some setups still run the installer through URLs like `/core/install.php/foo`. On shared hosting where you can't edit server config, the same guide has an .htaccess option. Blocking the installer doesn't affect `update.php` or normal updates.

Action items for today.
1. Find out what your website runs on. Ask your web designer, agency or host. If it isn't Drupal, you're done with this one.
2. If it's Drupal, run the three checks above or ask whoever manages the site to run them.
3. Block `/core/install.php` with the web server rule above. Drupal's guide says some managed hosts already block it, so test first.
4. Update to 10.6.22, 11.3.22 or 11.4.13. Drupal Steward customers are protected from known attack paths, but Drupal still says to upgrade.
5. If you're on an end-of-life version, plan the upgrade now. There is no patch for 11.2.x, 10.5.x, 9 or 8, so the block is your only cover until you move.
6. Make sure the web server can't write to `settings.php`. Drupal says that blocks some, but not all, of the attack paths.
7. If the installer was open, have someone look for signs of takeover. Our own advice: check for admin accounts you don't recognize and pages you didn't publish.
